## Decisions locked

1. **Scope cut:** `parallel` + `merge` only. Rationale: `parallel` is where the wall-clock speedup lives; `merge` (especially `llm_pick_best`) is the "pick the better of N" capability that turns parallel output into actual value. `cli_tool` and WebSocket are observability/UX improvements that don't change throughput.

2. **Default `fail_mode` for `parallel`:** `fast` (cancel siblings on first failure). Rationale: matches CI/CD behavior, fails fast so the operator can fix the issue and re-dispatch. Override to `slow` per-step when you want all branches to complete (e.g., for evaluation). Override to `ignore` when you only need ≥1 success.

3. **`merge.llm_pick_best` output shape:** Returns both `chosen_source` (which input was chosen, e.g. "hephaestus-impl") AND `judge_output` (the LLM's full reasoning). Rationale: the reasoning is gold for "why did we pick this?" audit. The "I want a follow-up" workflow can read `judge_output` and dispatch a new brief to Marvin to address the loser's specific weakness.

4. **LLM-merge implementation strategy:** Reuse the engine's existing `llm_call` path (whatever method exposes LLM calls today — `_exec_llm` if it exists, or fall back to a subprocess call to the venv Python with a clear error). Rationale: no new dependency on the not-yet-built `cli_tool` step. If `llm_call` is broken or missing, the LLM-merge strategies error gracefully with a clear "LLM path unavailable" message and the workflow can fall back to `first` strategy.

5. **Nesting limit for `parallel`:** 3 levels deep. Rationale: spec §9 Q2 recommendation, prevents infinite recursion in pathological workflows. Detected at parse time (deep parse validation), not at runtime.

6. **Step 4.6 status:** Stays `pending, deferrable`. Step 4.7 is independent of 4.6 (4.6 is YAML guardrails + workflow validator, defense-in-depth for sovereign outbound; 4.7 is new step types in the engine). 4.6 can run before or after 4.7 without blocking.

7. **Brief count:** 2 briefs (vs 3 for Steps 4.3-4.5). Brief 1 = build, Brief 2 = verification + closure. Rationale: this is a smaller, more focused scope than the prior 3-brief pattern; the implementation is well-defined and the verification is straightforward.
