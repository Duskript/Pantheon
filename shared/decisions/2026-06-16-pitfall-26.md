# 2026-06-16 — Pitfall #26 stuck-workflow resolution

**Status:** 19 stuck workflows identified and aborted. Conductor daemon
restarted. Script committed for future use.

## Context

Pitfall #26 (day 2): 20 Conductor workflows in dead state with
`dispatched_to=null`. Stuck since 13:55Z (engine fix mid-flight). The
state files were written but the dispatch files in `pending/<god>/`
were never written. The daemon never saw the work.

## Investigation

Scanned `conductor/state/wf_*.json` for stuck workflows
(`status in {in_progress, waiting_for_ack}` + `current_step is set` +
either `dispatched_to=None` or `status=waiting_for_ack`). Found **19
stuck workflows** (digest said 15-20; the count was at the upper
end).

| Stuck at step | Workflow | Step type | God | Count |
|---|---|---|---|---|
| notify-tallon | sovereign-publish-tallon-correction | nats_publish | - | 3 |
| active-goals | morning-briefing | god | thoth | 11 |
| deliver | morning-briefing | nats_publish | - | 2 |
| last30days-research | morning-briefing | god | thoth | 3 |

All 19 had empty `step_history` (the engine never got to
`_record_step_completion`). Root cause: the engine fix at 13:55Z
broke the dispatch-file write path in `_execute_step` mid-flight.
State mutations happened (start_workflow_sync) but the follow-up
`_exec_god_dispatch` / dispatch-file write was interrupted.

## Actions taken

### 1. Initial re-fire attempt (FAILED)

Wrote v2-shape dispatch files to `pending/thoth/<wf>_<step>.json` for
the 14 god-step workflows. Restarted the conductor daemon. Touched
files to trigger awatch. Daemon picked up the files (14 events fired)
but **all 14 were dropped with WARNING**:
`unmatched internal event handoff.completed/conductor — dropping`

**Why it failed:** The dispatch file model is for **inter-step
handoffs** between gods in an already-running workflow. The daemon's
`watch_pending` synthesizes a `handoff.completed` event and routes
it through the rule engine. But the rule engine has no rule
matching `from_god=conductor → to_god=thoth`. The
`daily-morning-briefing` rule only matches `schedule.cron` events
(see `conductor/rules/scheduling.yaml`). So the dispatch files
became dead letters.

The morning-briefing workflow is only started by the cron
(`0 7 * * 1-5` UTC). Once started, the engine runs each step
internally (via `_execute_step` → gateway → record_completion →
advance), not via dispatch files. The dispatch files are for the
god-to-god handoffs that happen between steps, but those handoffs
go through the rule engine, which doesn't have a `from_god=conductor`
rule.

**Lesson:** writing dispatch files for stuck first-step workflows
does not re-fire them. They need to be either:
- Manually re-dispatched via the bridge's `submit_handoff` (which
  mints a fresh `wf_<uuid8>` and starts from the FIRST step —
  would lose progress on multi-step workflows), OR
- Aborted and left for the next cron tick, OR
- The engine fix re-run.

### 2. Cleanup + abort all 19

Removed the 14 bogus dispatch files. Wrote `.aborted.json` manifests
for all 19 stuck workflows with `requires_manual_review: true` and
a `note` explaining the situation. The state files themselves were
left in place for the audit trail.

**Conductor daemon:** was inactive (dead) at session start.
Started via `systemctl --user start conductor.service`. Now active
(PID 219413, 23 active workflows in startup scan, gateway connected,
NATS subscribed, webhook on :8088).

1. Delete `pantheon/conductor/state/wf_<N>.aborted.json` (16 files).
2. Restore state files from `pantheon/conductor/state.backup.20260616_073816/`.
3. Restart the conductor daemon if needed (it was restarted to

## Memory / pitfall note (for future operators)

**Pitfall #26** is the "engine fix mid-flight broke the dispatch
file write" failure mode. Symptom: workflow state file is at
`current_step=X` + `dispatched_to=None` + `step_history=[]`. Fix:
abort the workflow, restart the conductor daemon if it was killed
in the same incident, and let the next cron tick (or manual
`start_workflow`) re-fire it.

**Pitfall #27** (new): the dispatch file model is for **inter-step
handoffs** in an already-running workflow, not for re-firing
stuck first-step workflows. Writing `pending/<god>/<wf>_<step>.json`
for a stuck workflow does NOT re-fire it — the rule engine has
no rule matching `from_god=conductor`, so the event is dropped.
Fix: abort and wait for cron, OR use the bridge's `start_workflow`
directly.
