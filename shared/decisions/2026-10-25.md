# 2026-10-25 — Decisions

## Pantheon inbox task runner: Hermes handoffs had been dead for an unknown period — root-caused and fixed

- **Context:** Four MCP mailbox handoffs to `hermes` (calendar lookup, dashboard relaunch, Google client-secret
  question, Google credential handover) all came back `status: failed` with
  `hermes: '<prompt>' is not a hermes command.`
- **Root cause:** `~/.hermes/scripts/pantheon-god-inbox-runner.py::task_command()` preferred
  `[~/.local/bin/<god>, prompt]` for every god with a wrapper. The god wrappers (`thoth`, `iris`, `marvin`,
  `apollo`, `caduceus`) parse a bare positional prompt themselves, but `~/.local/bin/hermes` is the **raw CLI
  passthrough** (`exec …/hermes "$@"`) — so the entire prompt was parsed as a *subcommand name* and the process
  exited 1. Pickup/result posts still landed in Discord, which made it read as a task failure rather than a
  dispatch bug.
- **Decision:** Special-case `hermes` in `task_command()` — bypass the wrapper and always build the explicit
  `[HERMES_BIN, "chat", …, "--query", prompt]` argv, and never pass `-p hermes` (Hermes is the root
  `HERMES_HOME`; `~/.hermes/profiles/hermes/` is a dormant near-empty duplicate).
- **Verification:** live end-to-end run against a temp inbox with Discord posting stubbed —
  `processed: True`, `hermes_task_status: completed`, `read: True`, real agent output in
  `hermes_task_result`. Also asserted the constructed argv for hermes vs thoth/marvin/iris/caduceus.
- **Lesson written to:** `conductor-handoff-inbox-monitoring` (dispatch pitfall) and `pantheon-bridge`
  (wrapper table caveat).
