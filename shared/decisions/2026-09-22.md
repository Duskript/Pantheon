## Genre-Lexicon maintenance: open handoffs (Apollo, sixth cycle)

### 1. Cron `f606e92fc6ee` prompt is stale — sixth consecutive cycle

The 02:00 daily "Genre Lexicon Expansion" job still instructs its executor to build and append
to `Codex-Apollo/knowledge/reference/Genre-Lexicon.md` and to follow the split-monolith blueprint.
That write target has been **retired since 2026-09-17**. The prompt has therefore been wrong for
eight calendar days and six consecutive firings, and each firing has had to re-derive the real
contract from the filesystem instead of trusting its own instructions — which is exactly the
failure mode that produced the `genres/INDEX.md` truncation drift between 2026-09-14 and 2026-09-17.

**Requested change (owner: Hermes / a human — outside Apollo's write scope):** rewrite the prompt to:

1. write each profile as `genres/<slug>.md` following the Genre DNA blueprint (five `##` sections,
   no `---`, no YAML frontmatter);
2. rebuild `genres/INDEX.md` from disk, using each file's own `# ` header as the row label —
   never a slug-derived label (the 2026-09-19 bug);
3. update the parent `reference/INDEX.md` genre-count cell and `Last updated` date;
4. pick candidates by parent-promises-child, hand-checking prose-parenthood because the automated
   gap scan cannot see it.

### 2. `auto-split-refs.py` `split_file()` replaces `genres/INDEX.md` instead of merging — sixth cycle

`~/pantheon/scripts/split-reference-files.py` (and the Apollo-profile copy at
`~/.hermes/profiles/apollo/scripts/auto-split-refs.py`), `split_file()` lines 158–173, writes
`genres/INDEX.md` from the current run's `created` list only. Any run that produces new files in
`genres/` therefore **overwrites the accumulated index**. This is the documented root cause of the
index drift reported on 2026-09-13 (145 `.md` files against a 5-row index).

**Requested change:** merge with the existing index — keep rows whose files still exist, add or
refresh this run's slugs, and skip the write entirely when a run produces no new files.

**Mitigation in force:** curated profiles now go to `genres/<slug>.md` directly, and `genres/` is in
the split script's `SKIP_DIRS`, so the script never scans or splits it and the index is currently
only touched by Apollo's own rebuild. The latent bug remains for any future workflow that does
stage a monolith.

**Decisions (Konan, 2026-09-22):**

1. **Phasing — approved with an added precondition:** `0 → 0.5 → 1 → 2 → 3`. Phase 0.5 (~1 h) must
   prove ONE applier's write actually reaches the serving path, with a read-back, before a rollback
   ledger is built around it. Rationale: the mechanism proposed as the proven template is a no-op.

   Config left untouched. Decouple implemented instead: local publish to the `relay:` block already

3. **Build ownership:** Hermes takes Phases 0–3 end-to-end. Hephaestus not involved.
4. **Defects:** folded into Phase 0, one GitHub issue per defect for the audit trail.

**Verification findings that changed the plan (read-only, reproducible):**

- `lib/forge_sweep.py` — the named "template" with 1,030 cycles — **has no caller anywhere**
  (all 53 cron jobs + systemd units checked). Its ledger is a *different file*
  (`~/.hermes/pantheon/forge-sweep-history.json`, 24,918 B) from the 1,030-cycle ledger.
- The 1,030 cycles belong to `ichor_benchmarks.WeightTuner`, driven by `ichor_tick._step_improve`.
  `WeightTuner.apply()` does `WEIGHTS.clear(); WEIGHTS.update(new)` on the **in-process module dict
  of a oneshot** that exits ~50 s later → never persisted, never seen by any gateway.
- Ledger `current` (`fts5 0.486203`) ≠ live `ichor_hybrid.WEIGHTS` (`fts5 0.09, graph 0.73`).
  `set_weight_override` has **zero callers**, so `_WEIGHT_OVERRIDE` is permanently `None` and served
  weights are the file constants. Nothing detects the divergence.
- The metric is a constant: recall `0.45` in **797/1030** cycles; **16/1030** cycles with a nonzero
  delta; **5 distinct weight sets** across 1,030 runs. `cycle()` drifts only when `delta > 0` →
  fixed point, not a loop.
- Tick journal dead-success lines: `drift=1` counts the boolean `drift_applied: True`
  (`ichor_tick.py:871-872`); `verify` prints `no data` unconditionally because `_step_verify`
  returns key `benchmark` while the formatter reads `benchmark_results`/`recall` (`:883-884`).
  **The verification step cannot verify itself.**
- `SOUL.md` "Code Quality Discipline" append is in **6 of 12** files, not fleet-wide; apollo's
  marker string differs (`auto-applied 2026-07-03`) → the marker check **duplicate-appends** rather
  than no-ops. No forge-append backups exist on disk.
- Exporter self-test: `block_rate: 1.0` reported as `healthy: true`; the 7 adjustments include text
  already live in the SOUL.md blocks (would ship a duplicate-append on first publish).

**Standing hazard, now confirmed in four places:** the clawforge export (`SKIPPED` + exit 0), the
tick `improve` step (`drift=1`), and the tick `verify` step (`no data`). Every loop needs an
assertion that it *did* something, not that it exited cleanly.
