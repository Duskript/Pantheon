## Decisions Made

### D3-D1: Drop-zone convention
**What:** File-drop connectors look for exports in `~/pantheon/connectors/drop-zone/{source}/`.
Currently `drop-zone/youtube/` for YouTube Takeout `watch-history.json` files.
**Why:** The connector is file-drop (not OAuth) for v0.3. Users need a known place to put exports.
The cron wrapper scans these directories, so the convention must be documented and stable.
**Alternatives considered:** Scanning `~/Downloads/` (too broad), requiring `--file` on every cron run (defeats automation).

### D3-D2: Processed file handling
**What:** After successful processing, files are renamed to `*.processed-<timestamp>` instead of
deleted or moved to a `processed/` subdirectory.
**Why:** The operator can inspect what was processed. The timestamp in the filename prevents
re-processing. If a connector run fails, the file is NOT renamed — the operator can fix and retry.

### D3-D3: Cron delivery mode
**What:** The cron job `pantheon-sync-connectors` uses `deliver=local` — no notification delivery.
**Why:** This is infrastructure plumbing, not a user-facing job. The sync.log is inspectable on disk.
Notifications would be noise. If a phase fails, the operator can check the log manually.
**Revisit if:** A monitoring/alerting system is built that should surface connector failures.

### D3-D4: Hotness integration pattern
**What:** The hotness phase uses a Python inline call that imports `HotnessTracker`, calls
`apply_decay()` then `promotion_candidates()` + `mark_promoted()` in a single pass.
**Why:** `hotness.py` is not a standalone script — it's a library module. The wrapper
avoids creating a separate hotness CLI for a two-method call. If hotness.py gains
a `run_maintenance()` entry point later, the wrapper can switch to it.
