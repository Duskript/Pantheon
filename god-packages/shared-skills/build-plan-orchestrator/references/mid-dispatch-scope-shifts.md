# Mid-Dispatch Scope Shifts

A reference for what to do when a dispatched task is wrong for the worker that's about to claim it, the scope is now redundant, or the build is blocked by something only clear after dispatch.

## The four patterns

### 1. **Fold a planning artifact into a build phase** (P0a case, Conductor UI build 2026-06-16)

**Signal:** A Phase 0 task is a planning artifact (a markdown doc that captures findings from reading another artifact) and the worker assigned to Phase 0 doesn't need to read the source artifact — the info is already in the build plan §3.

**Pattern:** Remove the task from its current phase, fold it into the phase where the source artifact actually gets read by the build worker. The planning doc still gets written — just by the right worker, in the right phase, as a side-effect of doing the build.

**Example:** P0a "re-inspect the mock" was a Phase 0 task that produced `docs/mock-inspection.md`. But the mock re-inspection only matters to whoever reads the mock to build the shell. That worker is Phase 1, not Phase 0. P0a moved to Phase 1, became a Phase 1 deliverable, written by the shell worker after they read the mock.

**Implementation:**
1. Patch the build plan §4 (Phase N description) to note the scope shift with date + reason
2. Patch the build plan §5 (Phase N+1 description) to add the deliverable
3. Edit the live kanban task body to match (or rely on the worker reading the plan §4+5, which is the source of truth)
4. Reassign to a profile that has the right skills
5. Unblock

### 2. **Strip skills and reassign when the worker crashes on missing skills** (Conductor UI Phase 0 case, 2026-06-16)

**Signal:** A task's first spawned run dies immediately with `Error: Unknown skill(s): <name>` and `gave_up` after failure_limit. The assignee's profile doesn't have one or more of the skills the task loaded.

**Pattern:** Strip the missing skills from the task's `skills` column (direct SQLite — see pitfall in `build-plan-orchestrator` SKILL.md), reassign to a profile that has the remaining skills, unblock.

**Example:** t5 loaded `pantheon-dev-workflow, build-spec-authoring, olympus-ui, thoth-qa-gate` for Iris's Phase 0 task. Iris's profile doesn't have `build-spec-authoring` or `thoth-qa-gate` (those are planner/reviewer skills, not UI/UX skills). Worker died. Fix: SQLite UPDATE to `["pantheon-dev-workflow", "olympus-ui"]`, reassign to Marvin (who has those), unblock. Marvin claimed it on the next daemon tick.

**Why this works:** The skills are force-loaded hints for the worker, not hard requirements. Stripping the planning skills doesn't break the coder work — Marvin builds fine with just `pantheon-dev-workflow, olympus-ui`. The QA gate stays in place because the Thoth review follow-on (auto-generated by t5 as a separate task) loads `thoth-qa-gate` on its own task.

### 3. **Defer a "later" task to a later phase** (P0b → already shipped case, Conductor UI 2026-06-16)

**Signal:** A task in Phase N was already completed before the chain dispatched (a parallel workstream finished it). Don't redo the work.

**Pattern:** Mark the task as already shipped in the plan, redirect downstream tasks to consume the artifact at the path it lives at, not re-author it.

**Example:** P0b "design the Conductor UI Soulforge interview" was a Phase 0 task. We designed and signed off on the interview before t5 dispatched (`docs/conductor-soulforge-interview-design.md`, 32K). The Phase 0 task body referenced P0b as "skeleton may already exist; verify and complete." The fix: leave P0b as a no-op in Phase 0, the file is already at the deliverable path, downstream tasks (`src/soulforge/groups.ts` in Phase 0, the Phase 4 visual editor) consume the file directly.

### 4. **Drop a task entirely when the value is below the cost** (always an option)

**Signal:** A task in the plan was useful when the plan was written, but between then and dispatch, the value diminished. E.g., a "research X" task when Konan already knows X.

**Pattern:** Document the drop in the plan §4 (with date + reason), remove from the file-by-file table, and don't dispatch. If the chain has already dispatched, mark the task's body as obsolete and don't unblock. The chain proceeds without it.

## When NOT to shift scope mid-dispatch

- **The shift breaks a dependency.** Don't move a task to a phase that comes before its dependencies. The build plan §4 has the dependency graph; respect it.
- **The shift crosses specialists mid-stream.** If Hephaestus has been working Phase 2 and you want to move a Phase 3 task to Iris, the context handoff cost is real. Prefer within-specialist shifts.
- **The shift is just "I changed my mind."** That's a normal operator decision, not a mid-dispatch scope shift. Just unblock with a new direction; the t3/t4/t5 chain handles it. Mid-dispatch scope shifts are for *structural* changes (worker can't run, task is redundant, plan section is wrong), not "do this differently."
- **The shift is to fix the operator's mistake, not the plan's.** If the operator said "use Tailwind" and the worker can't install Tailwind, the right move is to fix the install path, not the plan.

## The decision checklist

When a task is blocked / crashing / redundant, ask in order:

1. **Can the worker run with the current skills?** (If yes, just unblock and let it try.)
2. **Can the worker run with stripped skills?** (If yes, strip + reassign per pattern #2.)
3. **Is the task's deliverable already shipped?** (If yes, defer per pattern #3.)
4. **Is the task a planning artifact that belongs in a build phase?** (If yes, fold per pattern #1.)
5. **Is the task's value below its cost now?** (If yes, drop per pattern #4.)
6. **None of the above — investigate the underlying issue.** (Worker crash, missing deps, profile state. That's debugging, not scope-shifting.)

## Auditing the shift

Every mid-dispatch scope shift should be recorded in `~/pantheon/shared/decisions/YYYY-MM-DD-<project>-<phase>-scope-shift.md` with:
- What was decided
- What was the rationale
- What alternatives were considered
- What the reversibility is
- The build plan §4 patches (with date)
- The kanban task body changes (with date)

Two real instances of pattern #1 and #2 are now in the canonical record (Conductor UI build 2026-06-16). These are class signals, not one-offs. Future agents running a dispatched build chain should expect at least one mid-dispatch adjustment on any chain of >5 tasks.
